# WBS Core Quality Checklist (16 points)
Per the PMI Practice Standard for WBS as summarized in Buchtik. A WBS has core quality only when ALL items pass. Use this for the Quality Audit sheet (CREATE mode) and as the scoring rubric (AUDIT mode).

| # | Check | Pass criteria |
|---|-------|---------------|
| 1 | Deliverable oriented | Components are outcomes (nouns/adjectives), not tasks/activities/verbs |
| 2 | Defines the project scope | Reading the WBS + dictionary answers concrete scope questions (the "car test": no two stakeholders can picture different products) |
| 3 | Clarifies and communicates the work | Understandable to stakeholders who didn't build it |
| 4 | Contains 100% of the work | Nothing in scope is missing anywhere in the structure |
| 5 | Captures ALL deliverables incl. project management | A Project Management branch exists and is decomposed |
| 6 | 100% rule at every level | Each parent = exactly the sum of its children; no overlap or redundancy between siblings; verified per level |
| 7 | Work packages support task identification | Each work package is concrete enough to derive activities and milestones |
| 8 | Graphical, textual, or tabular breakdown provided | At least one clear representation exists |
| 9 | Noun-based naming | Components named with nouns and adjectives, consistent convention |
| 10 | Hierarchical structure of deliverables | Clear parent-child hierarchy; each element has exactly one parent |
| 11 | Coding scheme on every component | Unique WBS ID per component; hierarchy readable from the ID |
| 12 | At least two levels (one level of decomposition) | ≥2 levels always; ≥3 for projects of meaningful size/complexity |
| 13 | Created by those performing the work | Owners/doers involved in decomposition (or flagged for their review) |
| 14 | Built with stakeholder and expert input | Stakeholder review iterations planned or done |
| 15 | Evolves with progressive elaboration until baselined | Rolling-wave placeholders identified for unknown future work |
| 16 | Updated via change control after baseline | Post-approval changes route through formal change control |

## Additional defect patterns to flag in audits
- **Schedule leakage**: dependencies, dates, durations, or sequencing inside the WBS.
- **Parent treated as work package**: estimates/owners hung on components that have children.
- **Mixed sibling logic**: phases and deliverables mixed at the same level without rationale.
- **Under-decomposed vague branches**: a component that can't be assigned, estimated, and controlled.
- **Over-decomposition**: detail beyond what's needed to manage — control cost exceeds value.
- **Missing exclusions**: dictionary has no out-of-scope statements for ambiguity-prone packages.
- **LoE/discrete confusion**: LoE items presented as measurable deliverables without decomposition into artifacts.
